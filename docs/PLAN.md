# 목표와 계획

## 1. 한 줄 목표

**어떤 분야의 어떤 결과물이든, 내가 직접 쓴 것처럼 나오는 초안을 만든다.** 읽는 사람이 AI를 의심하지 않고, 나도 고치는 양이 적어야 한다.

## 2. 문제를 어떻게 보는가

AI 티가 나는 이유는 "말투"가 아니다. 모델이 기본값으로 내놓는 **평균적인 글**이기 때문이다.

- 구조가 매끈하다 (서두, 균등한 불릿, 요약 결말)
- 구체성이 없다 (내가 겪은 일, 숫자, 고유명사가 빠짐)
- 모든 걸 안전하게 말한다 (단정, 편향, 버릇이 없음)

사람의 글은 어색하고 울퉁불퉁한 부분이 곧 개성이다. 그래서 "자연스럽게 써줘"라고 시키는 것으로는 안 된다. **내 글이 AI 기본값과 어디가 다른지**를 데이터로 찾아서, 그 차이를 생성 단계에서 강제해야 한다.

그리고 내 스타일은 하나가 아니다.

| 분야 | 형태 | 내 스타일이 달라지는 지점 |
|---|---|---|
| 학교·캡스톤 | 보고서, 회의록, 발표 대본 | 격식, 근거 제시 방식, 용어 |
| 일상·소통 | 카톡, 메일, 커뮤니티 글 | 종결어미, 줄임말, 이모지 |
| 개발 | 코드 주석, 커밋 메시지, README | 길이, 영/한, 설명 깊이 |
| 설계·계산 | 계산서, 실험 노트 | 수식·단위·표 사용 습관 |

그래서 단위는 **분야 × 형태** 하나당 프로파일 하나다.

## 3. 접근 방식

파인튜닝부터 하지 않는다. 데이터가 적을 때는 아래가 더 싸고 더 잘 먹힌다.

```
내 글(코퍼스)
   │  ① 수치 분석 + AI 초안과 대조
   ▼
스타일 프로파일 (규칙 + 수치 + 대표 예문)  ←── ⑥ 내가 고친 diff로 갱신
   │  ② 생성 시 주입 + 슬롭 금지 목록
   ▼
초안 생성 ──→ ③ 슬롭 검사 / 스타일 거리 측정 ──→ ④ 재작성
   ▼
내가 수정 ──→ ⑤ 원본 vs 최종본 diff 저장
```

핵심 아이디어 두 가지:

1. **대조 학습.** 같은 주제를 AI에게 그냥 시킨 글과 내 글을 나란히 놓고, 차이를 규칙으로 뽑는다. "내가 이렇게 쓴다"보다 "AI는 이렇게 쓰는데 나는 안 그런다"가 훨씬 잘 쓰이는 규칙이 된다.
2. **수정 로그가 최고의 데이터.** AI 초안을 내가 어떻게 고쳤는지가 취향이 가장 정직하게 드러나는 곳이다. 이걸 계속 쌓는다.

최종 형태는 Claude Code 스킬(`/write-as-me <분야> <형태> <주제>`)로 만든다. 프로파일을 골라 읽고 쓰고 검사까지 돌린다.

## 4. 단계별 계획

### Phase 0. 범위 확정 (반나절)
- [ ] 분야×형태 목록을 확정한다. 처음엔 **3개만** 고른다 (자주 쓰고, 글이 많이 있고, 서로 많이 다른 것)
- [ ] 각 형태의 독자와 용도를 한 줄씩 적는다
- [ ] 성공 기준을 정한다 (아래 6번)

### Phase 1. 코퍼스 수집 (가장 중요, 가장 오래 걸림)
- [ ] 내가 직접 쓴 글을 `corpus/<분야>/<형태>/` 에 모은다. 형태당 최소 5편, 목표 15편
- [ ] 출처: 과제 보고서, 카톡 내보내기, 메일, 노트 앱, 깃 커밋/주석, 블로그, 디스코드·커뮤니티
- [ ] **AI가 쓰거나 고친 글은 제외한다.** 기존 `old/` 의 문서 대부분은 에이전트가 쓴 것이라 코퍼스로 쓰면 안 된다. 쓸 수 있는 건 내가 직접 쓴 프롬프트·메모뿐이다
- [ ] 퇴고 전 초안이 있으면 같이 둔다 (초안과 최종본의 차이도 스타일 정보)
- 산출물: 형태별 글 묶음 + 간단한 메타(독자, 공들인 정도)

### Phase 2. 슬롭 진단
- [ ] 코퍼스의 각 글 주제로 AI에게 **아무 스타일 지시 없이** 초안을 쓰게 한다
- [ ] 내 글과 AI 글을 나란히 비교해서 차이 표를 만든다 (구조, 어휘, 길이, 구체성, 어조)
- [ ] `slop/patterns_ko.md` 를 내 기준으로 고친다 (내가 실제로 쓰는 표현은 금지 목록에서 뺀다)
- 산출물: 분야·형태별 "AI는 이렇게, 나는 이렇게" 차이 목록

### Phase 3. 프로파일 추출
- [ ] `pipeline/` 에 분석 스크립트를 만든다: 문장·문단 길이, 종결어미 분포, 접속사, 불릿·헤더 빈도, 이모지, 외래어·약어 비율
- [ ] 수치 + 차이 목록 + 대표 예문 5~10개로 `profiles/<분야>_<형태>.md` 를 만든다 (`_TEMPLATE.md` 사용)
- [ ] 프로파일을 내가 직접 읽고 "이거 아닌데" 하는 부분을 고친다
- 산출물: 프로파일 3개

### Phase 4. 생성기
- [ ] 입력: 분야, 형태, 주제, **내가 가진 구체적 소재** (숫자, 겪은 일, 고유명사)
- [ ] 소재가 부족하면 AI가 지어내지 않고 **나에게 물어본다.** 구체성이 없는 게 슬롭의 가장 큰 원인이다
- [ ] 프로파일 + 유사 예문 few-shot + 금지 목록을 넣어 초안을 쓴다
- [ ] 자체 검사: 슬롭 패턴 적중 수, 수치 프로파일과의 거리. 기준을 넘으면 재작성한다
- [ ] Claude Code 스킬로 패키징
- 산출물: `/write-as-me` 스킬

### Phase 5. 평가
- [ ] **블라인드 테스트:** 내 글 / AI 기본 초안 / 이 시스템 출력을 섞어 놓고, 나(또는 친구)가 "누가 쓴 것 같나"를 맞힌다
- [ ] 같은 주제로 비교: 기본 AI vs 시스템 출력, 어느 쪽이 내 글 같은가
- [ ] 결과를 `evals/` 에 날짜별로 기록한다
- 산출물: 평가표, 실패 사례 목록

### Phase 6. 피드백 루프 (상시)
- [ ] 실제로 쓸 때마다 AI 초안과 내 최종본을 `feedback/` 에 저장한다
- [ ] 일정 건수가 쌓이면 diff를 분석해서 프로파일과 금지 목록을 갱신한다
- [ ] 갱신 전후로 Phase 5 평가를 다시 돌려서 실제로 나아졌는지 확인한다

### Phase 7. 확장
- 분야·형태 추가 (코드, 슬라이드, 설계 문서, 영어 글)
- 데이터가 충분해지면(형태당 수십 편 이상) 파인튜닝이나 스타일 분류기 검토
- 이미지·슬라이드 같은 비텍스트 결과물의 "내 스타일" (레이아웃, 색, 밀도)

## 5. 폴더 구조

README.md 의 표 참고. 분야·형태 이름은 영어 소문자 kebab-case로 통일한다 (`corpus/capstone/meeting-note/`).

## 6. 성공 기준 (숫자로)

| 지표 | 시작점 | 목표 |
|---|---|---|
| 블라인드 테스트 정답률 (AI 글을 AI라고 맞힘) | 기본 AI 초안으로 측정 | 시스템 출력은 50%에 가깝게 |
| 내가 고치는 양 (초안 대비 최종본 변경 비율) | 기본 AI 초안으로 측정 | 절반 이하로 |
| 슬롭 패턴 적중 수 (글 1편당) | 기본 AI 초안으로 측정 | 거의 0 |
| 수치 프로파일 거리 | 기본 AI 초안으로 측정 | 내 글 편 간 편차 안쪽 |

시작점을 먼저 재야 개선이 개선인지 알 수 있다. Phase 2에서 같이 측정한다.

## 7. 위험과 대비

| 위험 | 대비 |
|---|---|
| 코퍼스에 AI가 쓴 글이 섞임 | 수집 규칙으로 제외, 의심되면 뺀다 |
| 글이 너무 적음 | 카톡·메모처럼 짧은 글부터 모은다. 형태당 5편이면 시작 |
| 개성을 흉내 낸다고 버릇을 과장함 | 프로파일에 "빈도"를 같이 적는다 (예: 10편 중 3편) |
| 규칙만 따르고 알맹이는 슬롭 | 구체 소재를 입력으로 강제, 없으면 질문 |
| 내 글이 상황마다 일관되지 않음 | 형태·독자 단위로 잘게 나눈다 |
| 개인 글이 레포에 공개됨 | `corpus/` 를 git에서 제외했다. 레포가 공개면 `profiles/` 의 예문도 확인한다 |
